# Phase 8 — UI Design Contract

> Visual and interaction contract for Phase 8 (Data & Terrain Pipeline). Generated by gsd-ui-researcher, verified by gsd-ui-checker (7/7, 2026-10-24).
>
> **Scope: the `SiteFooter` map-sheet margin only (SHELL-04).** The roadmap says "The UI-SPEC covers only the footer legend". This contract covers four things: the full-bleed contour band (D-19), the decorative waypoint ticks (D-20), the sheet-margin grid with title, equidistance, true scale bar, corner coordinates, "last surveyed" and attribution, placed beside the existing identity block and links (D-18), and the static, no-motion rule (D-21). The terrain pipeline, photo data, images, highlights, hero, Map view and 404 are **out of scope**. This spec states only the metadata fields the footer reads and how they are formatted.
>
> **Baseline:** `07-UI-SPEC.md` (approved 2026-10-10) is the design system. This spec **inherits** its tokens v2, spacing scale, type roles, footer surface, interaction states and motion rule 3, and redefines none of them. If anything here seems to conflict with 07, 07 wins, except where this spec explicitly replaces the 07 "SiteFooter" table.
>
> **Source tags:** **[D-NN]** marks a locked user decision from `08-CONTEXT.md`. **[07]** marks something inherited from the Phase 7 UI-SPEC. **[REPO]** marks repo scouting. **[ARCH]**, **[PIT]** and **[STACK]** mark milestone research. **[UUPM]** marks a `ui-ux-pro-max` rule ID. **[SRC]** marks an external source with its URL. **Discretion (researcher)** marks one of the two items CONTEXT hands to this spec. **Default (researcher) — confirm at plan review** marks a value no upstream artifact fixed.

**Landmarks and focus (unchanged contracts):** one `<footer>` (contentinfo) per page, **no `<nav>` inside it** [07]. ### ① Contour band [D-19]

| Property | Spec |
|----------|------|
| Position | First child of `<footer>`, outside the `max-w-6xl` container, so it spans the footer's full width edge to edge. It sits under the existing `border-t border-line` |
| Source asset | The terrain pipeline's **`strip` LOD** contour SVG (`terrain.assets.contours.strip`, content-hashed under `/terrain/`) [ARCH §5]. The footer imports the URL from `data/generated/terrain.ts` and never hard-codes a filename |
| Asset geometry (requirement on the pipeline) | viewBox = the **full extent width** (west to east edge of the D-14 extent) × **one fifth of that width** in height, i.e. an aspect of exactly **5:1**, centred vertically on the Matterhorn summit's northing (a horizontal crop through the summit). With the ~11 km extent this is ≈ 11 × 2.2 km. If the summit lies within one tenth of the extent width of the south or north edge, the strip shifts to the nearest valid northing, and the strip's LV95 bbox is recorded in the metadata either way |
| Rendering | `ContourField lod="strip"`: `<div aria-hidden="true" class="bg-contour">` with `mask-image: url(<strip>)`, `mask-size: cover`, `mask-position: center`, `mask-repeat: no-repeat` (plus `-webkit-` prefixes) [ARCH §5]. Inline `style` is allowed by the CSP (`style-src 'self' 'unsafe-inline'`), and same-origin mask images fall under `img-src 'self'` [REPO `proxy.ts:9-10`]. Do not use `<img>` or `next/image`: an external SVG image cannot take the token colour |
| Box aspect | `aspect-[5/1]` below 640 px, `sm:aspect-[8/1]` from 640 px, `lg:aspect-[12/1]` from 1024 px |
| Resulting height | 375 → 75 px · 639 → 128 px · 640 → 80 px · 768 → 96 px · 1023 → 128 px · 1024 → 85 px · 1440 → ≈120 px · 1920 → 160 px · 2560 → ≈213 px (the footer width ÷ ratio; the stable scrollbar gutter takes a few px on desktop) |
| Why it stays true | The asset is 5:1, and every box is 5:1 or wider. `mask-size: cover` therefore always scales by **width**, so the band shows the **full extent width at every viewport** and crops only top and bottom, centred on the summit row. Horizontal metres per pixel = `extentWidthM / footerWidthPx` at every breakpoint. The scale bar uses the same equation (③), so it is true by construction, with no JS and no measuring |
| Line styling (inside the strip SVG, requirement on the pipeline) | Strokes only, no fills. `vector-effect="non-scaling-stroke"`, `stroke-width="1"`, so lines render at 1 CSS px at every scale. **Index contours** (every 5th interval) use mask opacity 1.0, which shows the token at its full 0.14 alpha. Intermediate contours use `stroke-opacity="0.6"` (≈0.084 effective). This is the swisstopo index-contour convention, expressed in one token. Default (researcher) — confirm at plan review |
| Line density (requirement on the pipeline) | The strip interval must keep rendered contours **at least 2 px apart at 375 px** across the steep faces (≈29 m/px there). **100 m (index every 500 m) is the expected value.** The footer shows whatever interval the asset was built with (④ Equidistance) and never hard-codes it |
| Neatline | `border-b border-line` on the band box: a 1 px decorative line that closes the band like a sheet neatline. The ticks stand on it |
| Interaction | None. No hover, no pointer events (`pointer-events-none` on the band), no link, no tooltip |
| Motion | **None** [D-21]. No draw-in, no drift, no scroll-driven parallax (overrides ARCHITECTURE §5's footer parallax idea). No `animation`, `transition` or `animation-timeline` on any band element. The v1 `.contour-animate` class must not be used |

### ② Waypoint ticks [D-20]

| Property | Spec |
|----------|------|
| What | One tick per photo with a position in the photo data (four photos today), at the photo's **easting**, standing on the band's bottom neatline. These are margin ticks in the cartographic sense: they mark the position along the sheet's horizontal axis. Placing them by easting alone means a crop can never push a tick out of view, because the band always shows the full extent width. The Zermatt photos lie 3–4 km north of the summit row, outside every vertical crop |
| Position | `left: <u × 100>%`, where `u = (E − E_west) / extentWidthM` comes from the terrain metadata (the same terrain-UV space Phase 10 markers use [ARCH §5]), rounded to 4 decimals at build time for deterministic output. `bottom: 0`. No translate (the tick is 1 px wide) |
| Exact position (3 digital photos) | `<span class="absolute bottom-0 h-4 w-px bg-ink-muted">`: a solid 1 × 16 px line |
| Approximate position (film scan, Riffelsee) [D-02, DATA-04] | `<span class="absolute bottom-0 h-4 w-0 border-l border-dashed border-ink-muted">`: the same 16 px, **dashed**. Shape, not colour, carries the difference [UUPM `color-not-only`]. It is driven by `position.approximate === true` in the photo data, never by a hard-coded id |
| Semantics | Every tick is `aria-hidden="true"` (inherited from the band). They are not links, add no tab stops and have no `title` or tooltip [D-20]. A screen-reader user loses nothing, because the photo locations are presented properly in Phase 10 |
| Close ticks | img-0605 and img-0629 are ≈225 m apart, ≈7.7 px at 375 px, so they render as two distinct lines. No collision handling is needed. If a future photo comes within 2 px at 375 px of another, the ticks may overlap (decorative, acceptable) |
| Count | Driven by the data. Zero photos with a position renders zero ticks, and the band still renders. The footer never renders a tick for a photo without a position |

#### Scale bar (true at every breakpoint) [D-18]

| Property | Spec |
|----------|------|
| Principle | The band shows `extentWidthM` across the footer's full width (①). A bar for length `L` metres is therefore `L / extentWidthM` of the **footer** width. The `<footer>` carries `@container` (`container-type: inline-size`), so the bar width is `calc(100cqw * <L / extentWidthM>)`. `cqw` resolves against the footer, the band's own width, from inside the padded container. Pure CSS, server-rendered, deterministic. **No other `@container` may sit between the footer and the bar** |
| Fraction | `L / extentWidthM`, computed at render from metadata, written with `toFixed(6)` into inline `style={{ width: \`calc(100cqw * ${fraction})\` }}` |
| Length tiers (each tier's bar fits its smallest cell) | **2 km** below 1024 px (two 1 km segments; labels `0` `1` `2 km`) → 68 px at 375, 186 px at 1023. **1 km** from 1024 to 1791 px (two 500 m segments; labels `0` `500` `1 km`) → 93–163 px. **500 m** from 1792 px (two 250 m segments; labels `0` `250` `500 m`) → 81 px at 1792, 175 px at 3840. Figures assume an ~11 km extent, and the tier rule must hold for any extent from 10 to 12 km (see verification). Viewports above 4096 px are not guaranteed to fit, and the bar may then overflow into the 32 px column gap (still true, just wider) |
| Tier switching | Three sibling variants in the `dd`, each `hidden` outside its range: `flex lg:hidden` / `hidden lg:flex min-[1792px]:hidden` / `hidden min-[1792px]:flex`. `display: none` removes the inactive variants from the accessibility tree, so exactly one is announced |
| Bar | `<div class="flex h-2 border border-ink-muted" style="width: calc(100cqw * f)">` holding two `flex-1` halves: the first `bg-ink-muted` (filled), the second empty (hollow). This is the alternating swisstopo segment style. The segment edges are the ticks at 0, ½ and 1 |
| Labels | `<div class="relative mt-1 h-5 font-mono text-sm text-ink-muted tabular-nums" aria-hidden="true">` with three absolutely positioned spans, each **centred on its tick by digit count**, because mono glyphs are exactly `1ch`: `left: calc(<tick%> - <digits × 0.5>ch)`. The unit follows the last number after a no-break space (U+00A0), so `2 km` places the "2" over the right end and lets "km" run past it. Example 2 km tier: `0` at `left: -0.5ch`, `1` at `calc(50% - 0.5ch)`, `2 km` at `calc(100% - 0.5ch)` |
| Accessible text | Each variant carries `<span class="sr-only">Scale bar, 2 km</span>` (or `1 km`, `500 m`). The visual labels are `aria-hidden`, so a screen reader hears "Scale, Scale bar, 2 km" once and not "0 1 2 km" |
| Non-text contrast | `ink-muted` on `surface-raised` 8.35:1 ✓ (≥3:1) |

#### Formatting rules (pure functions, unit-tested, no `Intl`)

| Field | Metadata source (read-only, from `data/generated/terrain.ts`) | Format | Example |
|-------|----------------------------------------------------------------|--------|---------|
| Equidistance | `contours.strip.intervalM` (the interval the drawn band was built with) | Integer metres, U+00A0, `m` | `100 m` |
| Scale | `extent.widthM` (= strip width in metres) | Bar as above | — |
| Extent (LV95) | `extent.lv95 = { west, south, east, north }` (EPSG:2056, metres) | Two lines, SW corner then NE corner: `SW 2’612’000, 1’088’000` / `NE 2’623’000, 1’099’000`. Easting first, then northing. Whole metres (round half up). Recommendation to the terrain plan (not a footer requirement): snap the extent to whole kilometres in LV95, so the corner values read as clean sheet-grid values like a swisstopo margin.

#### Discretion decisions (researcher; not user decisions)

| Item | Decision | One-line rationale |
|------|----------|--------------------|
| Corner-coordinate format (WGS84 vs LV95) | **LV95 (EPSG:2056)**, labelled `Extent (LV95)` | The DEM and the D-14 extent are defined in LV95, so the corners are exact (and, if snapped, round) values printed the way a swisstopo sheet margin prints them. WGS84 corners would be converted approximations of a rectangle that is not aligned to latitude and longitude. Photo coordinates elsewhere (EXIF strip, Phase 10) stay WGS84 at 4 decimals; the explicit "LV95" label prevents confusion |
| "Last surveyed" source (DEM edition vs terrain build date) | **DEM product edition** (`dem.edition`, e.g. `June 2026`, the swissALTIRegio update of 2026-06-25 [SRC](https://www.swisstopo.admin.ch/en/height-model-swissaltiregio-update-20260625)) | "Surveyed" describes the data, not the script run. A build date would change on every rebuild, misstate the survey age and make every footer screenshot non-deterministic |

### Static variant and determinism (D-21, 07 motion rule 3)

- `SiteFooter` imports **nothing from `motion/react`**, adds no `'use client'`, uses no hooks and no router, and stays a Server Component in the default shell. It must also render unchanged inside `global-error` (`'use client'`, `SiteChrome variant="static"`), where it is client-rendered. So everything it imports, including `data/generated/terrain.ts`, must be **client-safe and Jest-safe**: plain serialisable constants, no `fs`, no `d3-contour`, no `sharp`, and no contour path data (only the asset URL and scalars) [PIT 9; CONTEXT "d3-contour kept out of Jest-imported components"].
- No randomness, no `Date.now()` in the margin (the copyright year is the existing exception), no locale APIs, and fixed decimal rounding for every percentage and fraction. The same metadata always produces byte-identical HTML.
- No `motion-safe:` or `motion-reduce:` variants are needed, because nothing in the margin moves. Under `prefers-reduced-motion: reduce` the footer is identical.

### Metadata absent or invalid at build time

**There is no runtime fallback UI.** The footer imports typed metadata from the committed generated file. A missing file, a missing field or a failed `--check` is a **build or CI failure** (`tsc`, the generator's zod validation, `npm run lint`), never a footer that renders with `—`, an empty scale bar or a guessed equidistance. This follows the 07 precedent for `site.email` (a required type fails `tsc` rather than shipping a partial footer). Planner consequence: the footer plan **depends on** the terrain plan that writes `data/generated/terrain.ts` and the strip asset.

**Asset fails to load at runtime** (offline before precache, or a network error): the mask shows nothing, so the band is plain `surface-raised` with its neatline and ticks. There is no broken-image glyph, because a mask has none, and no layout shift, because the aspect ratio reserves the height. The strip URL must be added to the service-worker precache so `/offline` keeps its band [ARCH §2 integration; roadmap scope note].
