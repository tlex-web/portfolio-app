### Merge enforcement

Live repository settings on 2026-11-05:
- `branches/main/protection` answers 404 "Branch not protected".
- `required_status_checks` is empty with enforcement `off`.
- `rules/branches/main` is `[]`. The one active ruleset, `automated-actions`, does not apply to `main`.

| Record | Says |
|--------|------|
| 07-UAT test 3 | `pass`: the three jobs are Required on `main` |
| STATE.md | "RESOLVED at Phase 07 UAT: Tim confirmed the three jobs are Required on main" |
| 07-VERIFICATION | "Without this the CI guardrails in SC1 fail a run but do not block a merge" |

Whether the setting was removed later or never applied can't be told from here. The effect is visible on #109, which merged while its E2E job was running and with its CodeQL check failed, and production deployed about two minutes later, before CI had a verdict. That E2E job passed about 34 minutes after the merge, so this merge happened to be safe.

**Why this is not `gaps_found`:** GUARD-02 to GUARD-05 say CI *fails* on a violation, and it does. The Phase 7 goal is broader, guardrails that catch problems "before they ship", and that part doesn't hold until the checks are required. If you read the goal as binding, treat this as a gap. It closes with one settings change.

**When you turn it on:**
- Commits marked `[ci skip]` produce no checks, so a required check on such a head commit stays pending and blocks the PR. PR #109's head `1f300e7` is one of these, and GSD's ship step writes them.
- Vercel deploys on push regardless, so a required check only protects PR merges. A direct push to `main` still needs blocking separately.
- Decide whether `E2E Tests` joins the required set. It's the most complete check and the slowest, at about 37 minutes of test time on the last full run.

### Axe 4.14 label rule

All 18 E2E failures on Dependabot PR #111 are one rule, `label-content-name-mismatch` (WCAG 2.5.3, Level A), on the same six audit tests in each of the three engines. It ships in the pinned 4.13.0 as an experimental rule that doesn't run by default, which is why the gate is green today. Running only that rule on production at 1440 px reports 13 elements:

| Elements | Accessible name | Visible text | Reading |
|----------|-----------------|--------------|---------|
| 4 trail signs on Home (2 signs, 2 placements) | `Photographs, 4 waypoints` | `Photographs` / `4 waypoints` | Rule quirk: every visible string is in the name, in order |
| 4 map plates | `Matterhorn from Zermatt, 1,617 m` | `Matterhorn from Zermatt` / `1,617 m` | Rule quirk, same reason |
| 1 end-block link on `/projects/box` | `coin-flip, next route` | `coin-flip` / `Next route` | Rule quirk, same reason |
| 4 grid tiles | `Matterhorn from Zermatt` | Title, plus `Zermatt · 1,617 m · Sep 2021` | **Real, small:** the title works for speech control, but `aria-label` hides the place, altitude and date from screen-reader users on that link |

The "quirk" reading is my interpretation of WCAG 2.5.3, not a result from a screen reader or speech-control test. The grid fix is a small change to the tile's name; the map plates already show the pattern. The other nine will still fail the gate on axe 4.14 until they're rewritten or the rule is explicitly configured, so that upgrade needs a decision.
