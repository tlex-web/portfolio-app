<task type="checkpoint:decision" gate="blocking">
  <decision>Should the service worker register in development mode?</decision>
  <context>
Current implementation has a production-only guard (line 10):
```typescript
process.env.NODE_ENV === 'production'
```

This is common practice (service workers can complicate debugging), but it prevents testing SW behavior in dev.

The primary bug is the load event race condition (separate fix), but the production guard also contributes to UAT gap 3 (SW not visible during testing).
  </context>
  <options>
    <option id="allow-dev">
      <name>Allow dev registration (remove production guard)</name>
      <pros>
        - Can test service worker behavior locally without production builds
        - Easier to verify cache invalidation, update lifecycle, and offline behavior
        - Matches production environment more closely during development
      </pros>
      <cons>
        - Service worker may cache assets aggressively making hot-reload confusing
        - Debugging can be harder (need to unregister SW to see uncached changes)
        - DevTools > Application > Service Workers shows "Update on reload" option to mitigate
      </cons>
    </option>
    <option id="keep-production">
      <name>Keep production-only guard</name>
      <pros>
        - Standard practice (many frameworks skip SW in dev)
        - Cleaner development experience (no cache interference)
        - Fewer surprises for developers unfamiliar with service workers
      </pros>
      <cons>
        - Can't test service worker behavior without production builds
        - UAT testing requires building and serving production build (slower feedback loop)
        - Gap between dev and production environments
      </cons>
    </option>
  </options>
  <resume-signal>Select: allow-dev or keep-production</resume-signal>
</task>

  <action>
Fix the service worker registration race condition and apply the user's decision from Task 1.

**MANDATORY FIX (always do this):**
Remove the `window.addEventListener('load', ...)` wrapper (lines 12-36). This wrapper causes a race condition -- in a hydrated Next.js app, the load event has already fired by the time React hydration completes and useEffect runs, so the callback never executes even in production.

**Change from:**
```typescript
useEffect(() => {
  if (
    typeof window !== 'undefined' &&
    'serviceWorker' in navigator &&
    process.env.NODE_ENV === 'production'
  ) {
    window.addEventListener('load', () => {
      navigator.serviceWorker.register('/service-worker.js')
        .then((registration) => {
          // ... lifecycle listeners ...
        })
        .catch(() => {
          // ... error handling ...
        });
    });

    navigator.serviceWorker.addEventListener('controllerchange', () => {
      // ... controller change handler ...
    });
  }
}, []);
```

**Change to (structure):**
```typescript
useEffect(() => {
  if (
    typeof window !== 'undefined' &&
    'serviceWorker' in navigator
    // DECISION: Add production check here if user chose "keep-production"
  ) {
    // DIRECT CALL (no load event wrapper)
    navigator.serviceWorker.register('/service-worker.js')
      .then((registration) => {
        // ... lifecycle listeners (updatefound, statechange) ...
        // ... periodic update check (setInterval) ...
      })
      .catch(() => {
        // ... silent error in production ...
      });

    // controllerchange listener (outside registration callback)
    navigator.serviceWorker.addEventListener('controllerchange', () => {
      // ... controller change handler ...
    });
  }
}, []);
```

**Apply user decision:**

**If user chose "allow-dev":**
- Remove the `process.env.NODE_ENV === 'production'` condition entirely
- Only keep `typeof window !== 'undefined' && 'serviceWorker' in navigator`

**If user chose "keep-production":**
- Keep the `process.env.NODE_ENV === 'production'` condition
- Condition becomes: `typeof window !== 'undefined' && 'serviceWorker' in navigator && process.env.NODE_ENV === 'production'`

**Preserve existing logic:**
- Keep updatefound listener (lines 17-26)
- Keep periodic update check with setInterval (lines 29-31)
- Keep controllerchange listener (lines 38-42)
- Keep silent error handling (lines 33-35)
- Keep all comments explaining the silent update lifecycle

**Implementation notes:**
- Call navigator.serviceWorker.register() DIRECTLY in the useEffect body (not inside a load listener)
- The controllerchange listener should be registered outside the registration promise chain (as it currently is, line 39)
- Do not add any console.log statements (plan 02-03 removed them for silent updates)
