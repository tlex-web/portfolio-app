## Planner decisions (not Tim decisions)

- **Module layout (CONTEXT discretion):** the id list is Home data and goes in `data/home.ts`; `homeInput` and `homeLowestDemM` go in `lib/ascent/waypoints.ts`, which already imports the generated photos, editorial copy and manifest. A separate `lib/ascent/home.ts` would import `buildWaypoints` while `buildWaypoints` defaults to `homeInput`, a circular import.
- **Footer reads a client-light module (plan-check feedback):** `app/global-error.tsx` is a client component that renders the footer, so whatever the footer imports ships in a client chunk. The footer therefore imports `homePhotos` from the small `lib/ascent/home-photos.ts` (generated photos plus the id list), not `homeInput` from `waypoints.ts`, which would pull the editorial copy and the image manifest into that chunk. `homeInput` builds on `homePhotos`, so the membership rule exists once. The phase-wide client-chunk budget measured from 15-01's phase-base total (checked in 15-11 and 15-16) covers this plan's growth.
- **Footer tick order:** the footer maps `homePhotos()`, which keeps the generated module's order (filtering preserves order), so the tick markup is identical to today's, not re-sorted by height.
- **Success-criterion-1 mechanism (RESEARCH Assumption A5):** `jest.isolateModulesAsync` with `jest.doMock` of `@/data/generated/photos` and dynamic imports, not a hoisted `jest.mock`, so two variants live in one file and the modules under test are typed.
- **D-07 "a test or the build" (RESEARCH Open Question 2):** a Jest test (Task 2) plus tsc typing of the ids (`as const satisfies readonly PhotoId[]`, Task 1). The generators cannot import `@/` TypeScript modules, so a build-time check would duplicate the list.
